# Где живёт код

Два репозитория, каждый в двух местах — GitHub и внутренний GitLab.

| что | GitHub | GitLab |
|---|---|---|
| форк Docmost | `Altair666/docmost`, ветка `custom-sso-integration` | `grist_additional_widgets/docmost` |
| серверный модуль | `Altair666/docmost-custom-sso`, ветка `main` | `grist_additional_widgets/docmost-custom-sso` |

Модуль подключён сабмодулем в `apps/server/src/custom-sso`.

## Отправка изменений

```
deploy/push-all.sh
```

Скрипт отправляет оба репозитория в оба места **по очереди и с потолком
по времени**. Это не прихоть: у `origin` два адреса отправки, и когда
GitHub задумывается, обычный `git push origin` висит вместе с ним, а что
именно доехало — непонятно. Здесь у каждого адреса свой срок ожидания и
свой ответ.

Правки в сабмодуле отправляются **первыми**, и только потом в форке
обновляется указатель:

```
cd apps/server/src/custom-sso && git commit -am '...'
cd - && git add apps/server/src/custom-sso && git commit -m '...'
deploy/push-all.sh
```

## Доступ

Оба токена лежат в `/root/.git-credentials` с правами 600, git
подставляет их сам через `credential.helper store`. В адресах удалённых
токенов **нет** — иначе они светятся в каждом `git remote -v`.

Сертификат у GitLab внутренний, поэтому проверка отключена точечно для
этого хоста:

```
git config --global http."https://gitlab.mp-lab.ru/".sslVerify false
```

**Грабли, на которые я наступил.** Раньше токен GitHub был вшит прямо в
адрес отправки. Когда я переписывал адреса под двойной пуш, я его затёр
— и `git push` стал молча ждать ввода пароля, зависая до упора. Внешне
это выглядело как проблемы с сетью, хотя `curl` к пути записи отвечал
401 за четверть секунды. Отсюда правило: пароли держим в хранилище,
адреса оставляем чистыми.

## Что осталось на GitHub

Адрес сабмодуля в `.gitmodules` указывает на GitHub. Свежий клон из
GitLab потянет модуль всё равно оттуда — если нужна полная
независимость, адрес надо переписать, но тогда сломаются существующие
клоны.
